# HERO IPMI B2a：首次状态 FF 的诊断版

针对 `HEROIPMI-003.TXT`：B2 第一次读 BMC 通信状态得到 FF，PCI 读取函数本身返回成功，程序在发出任何 KCS 请求字节之前停止。临时 PCI Command 位已恢复，未执行 I 或 F。用户确认当时 BMC 网页正常，003 前没有运行过 B2，只重启过一次主机以进入 BIOS，故还需单独检查重启后的主机通信入口；重启是否致因尚未确定。

B2a 修正这一情形的错误名称为 `KCS_STATUS_ALL_FF`，并显示状态读取、数据读取和写操作次数。新增 **S** 仅采样状态，不重置扩展卡，不修改 PCI 桥或 BMC 配置，不自动重发 IPMI 请求。它用于补充证据，不能保证修好通信。

## 这轮怎么运行

1. 保留旧日志。把本包 `USB` 目录**里面**的 `EFI` 和 `HERO-PROBE-USB.TAG` 一起更新到 FAT32 U 盘根目录。启动后确认标题为 **HERO IPMI FAN B2a**。目标仍是 HERO BIOS 3107，无需降级或刷 BIOS。
2. 按屏幕提示 **E/P** 读取基线。如果再次出现 `KCS_STATUS_ALL_FF` 并提供 S，按 **S** 采样约 30 秒。期间显示每秒的 PCI 状态和 KCS 状态，不向 BMC 发送命令。
3. 采样结束后程序会恢复 PCI、关闭日志，按 **Q** 返回启动菜单。如果通信已经恢复并能读出传感器目录，**本轮先按 Q 完成记录，再按 Q 返回，不按 I/F**。请提供新生成的 `HEROIPMI-xxx.TXT`。

本轮无须重启 BMC、拔卡或完全断电来“试着恢复”；先保留当前故障下的采样，才能判断它是否自行变化。若 PCI 恢复显示不确定，保留日志并重启主机重新初始化 PCI；该操作不代表清除了此前的 BMC 设置。

## S 的范围与结果

S 只在**第一笔请求发送前读到 FF、尚无 KCS 写入或数据读取、日志可写**时提供。最多采集 31 次状态，间隔 1 秒，每次先核对同一 PCI 功能的身份、BAR 与内存解码位，然后读取 `BAR1+E8C` 状态寄存器。遇到 PCI 变化、读取或日志失败就停止。

- `all_ff=31 other=0`：这约 30 秒里状态持续为 FF，仍需查主机接口/映射路径，不能据此直接认定卡损坏。
- 出现非 FF：访问结果在采样期间变化了，但单独的状态值不能证明 IPMI 请求已经能完成。
- `kcs_write_attempts=0 kcs_data_reads=0`：S 阶段未写 KCS，也未读取会消耗响应的数据寄存器。

S 即使看到 00 或其他状态，也不会自动重发 Get Device ID、继续初始化或启动风扇测试。程序随后恢复临时 PCI 内存访问位并退出。

## 与 B2 的关系

原 B2 的 E/P、I、F、R 路径仍保留。I 会发送原 B1 初始化，F 会修改 CHA_FAN1 的转速映射和扫描状态；**因此整个程序不能笼统称为只读工具**。本轮仅使用 E/P 和必要时的 S。E 仍会临时设置扩展卡 PCI Command 内存解码位，并在正常退出及已处理错误路径恢复、读回；死机或断电不能执行清理。

历史 B1 的 4 项温度和 4 项电压有效读数没有被本次 FF 日志推翻；本次没有风扇测试结果，也未证明旧初始化是否持续。旧 B2 包、原始日志及 CAP 保持原样。

## 软件检查

交付 B2a EFI 的实际机器码通过 134 个离线场景：原 B2 的 121 个场景，以及 13 个 S/FF 诊断场景。新增场景检查持续 FF、变为 00/忙状态后仍不发命令、拒绝 S、旧标记、日志失败、PCI/BAR/解码变化、读取失败和计时等待失败。另对旧 B2 的实际 EFI 回放 003 的首次 FF 条件，确认 0 次 KCS 写入及 PCI 恢复路径。

所有 `example-MOCK-*` 为模拟日志。真实 003 分析在 `evidence/B2连接中止分析.md`；前次 BMC handler 的 11 个 ARM 离线检查随来源资料保留，并非新增实机验证。B2a 尚无实机结果。

源码和脚本依赖现有 BIOS 工作区的工具及证据，不是独立安装环境。本包只有 UEFI 应用，不含 BIOS/BMC 刷写镜像。
