# Local bootstrap validation

The production candidate EFI is 9,216 bytes, SHA-256 `7308cd9fec2aa06fb7a30684eb365063b86af2b1118cde16fc24f52fbaaf0887`. The ISO is 32,571,392 bytes, SHA-256 `4e70bb0abfc285849301a6829b1ac51cae914d65025e135b971b06dd47d25d18`. The exact production ISO has booted through its own EFI loader and the official Linux EFI stub to the custom PID1 under OVMF over both SATA and USB optical transports. Both produced the expected 482-byte non-target DMI refusal, CRC32 `992131CF`, with zero PID1 modules and zero userspace SG_IO calls. This is a transport/refusal result, not an ASUS hardware pass.

The fixture-contract bootstrap SHA-256 is `57efc935eb41fd6f604831c6d708bc44c90e60985c6c802a6ede7722f51c748c`. The fixture and production builds use the same bootstrap source, different pinned payload contracts. Both separate-directory rebuilds produced identical respective EFI bytes. The applications use PE timestamp 0 and no imports.

The valid EFI consumer fixture checks the exact UTF-16 load options, LoadFile2 size negotiation, copied initrd bytes, invalid arguments, wrong BootPolicy/path, and 16 guard bytes beyond the destination. It then deliberately returns EFI_SUCCESS. The bootstrap displays `LC01_BOOT_STOP kernel_returned` and stays alive instead of returning to firmware. Each VM was observed after the terminal marker, screen-captured, and stopped externally through QMP. This is a bounded observation of the nonreturning code path, not a claim that every firmware or external watchdog can never reset a machine.

The six seed tests require only zero-size/NULL-buffer queries. They detect any request for seed contents and any SetVariable call after the bootstrap begins querying; none occurred. The test DXE is TCG-only and exists only in isolated test firmware copies. A normal OVMF run without this fixture proves the absent-seed route.

The native fault suite covers watchdog failure, loader path mismatch, wrong/missing own filesystem, OpenVolume/GetInfo/Read/Close/allocation errors, invalid file metadata, directory substitution, short reads, unexpected EOF bytes, malformed device path, existing initrd provider, protocol-install failure, kernel LoadImage failure, child-device/path mismatch, StartImage error, and successful return. All unexpected file or runtime write service calls trap. All tested FileOpen calls use mode READ and attributes zero. Allocated-buffer guards remain unchanged.

Both readonly ISO and intentionally writable FAT image bytes were unchanged after completed fixture runs. This proves the behavior observed with these local firmware implementations and files. It does not imply that arbitrary firmware internals or hardware drivers have zero effects.

Two earlier construction/policy results are retained as history: a 64 MiB El Torito image with an underspecified sector count failed before loading BOOTX64; the corrected layout uses a complete 31 MiB FAT extent. The original strict ReadOnly metadata policy rejected QEMU USB optical media even though the ISO itself was opened readonly. The parent explicitly approved treating that flag as logged metadata because the loader never invokes write methods and executes only separately verified RAM buffers. The final fixture hash above passes both USB and writable-FAT cases without changing the files.

The frozen production contract is `candidate/contract.json`; `candidate/media_manifest.json` binds the three files in the ISO. The kernel SHA-256 is `9d6eff6e7bcd5f5fba623f7a44c565ca6914da2b91110a8dc72a3a63cb088693`, custom initrd SHA-256 is `3f1e21419c1b0dd82ac0a23d526bfa647084c9f1edcad2f649051283b1ec6989`, and command-line ASCII SHA-256 is `db6c14aa1420215013d0e233c9258fc909660fb6a6830c746ff1a070d26ee294`. No serial-debug token, noapic option, shell, test fixture, or stock Alpine initramfs is in the candidate.

The actual ISO tests use QEMU TCG single-thread mode with `-icount shift=3,sleep=off -rtc base=utc,clock=vm`. Earlier provisional ISO tests using host-clock TCG hit the Linux early `IO-APIC + timer doesn't work` panic before PID1. Failure logs and debug variants remain under `tests/linux-runs` and `tests/debug_variants`. TPL was 4 and IF enabled before StartImage; avoiding watchdog calls, loading by file path, silencing the LoadFile2 callback, and disabling emulated HPET did not cure those runs. The same provisional ISO succeeded after only the VM clock/profile change. A fw_cfg bypass control with the same optical medium also succeeded, but it does not validate this loader. These observations implicate the virtual timing environment; the precise single-knob cause is not established by that combined profile change.

QEMU documents that icount advances virtual time from executed instructions and is not cycle-accurate. This setting changes only the simulator, not any production artifact or kernel parameter. It proves the tested UEFI/EFI-stub/PID1 path and refusal boundary under that virtual environment; it cannot prove ASUS interrupt routing, BMC USB behavior, physical timing, firmware-internal writes, or successful capacity probing of the real target. See [QEMU invocation reference](https://www.qemu.org/docs/master/system/invocation.html#hxtool-0) and the separately retained failure evidence. A similar upstream [QEMU issue 2832](https://gitlab.com/qemu-project/qemu/-/issues/2832) is context only, not proof of the same root cause here.

No BMC connection, target deployment, physical reboot, firmware flash, or stock Alpine initramfs execution was performed by this task.
