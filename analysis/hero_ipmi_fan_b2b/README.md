# HERO IPMI B2b：等待接口稳定后继续测试

004 日志已执行 S：第一次状态 FF，随后 31 次采样全部为 00，期间没有 KCS 写入，PCI 设置也正常恢复。这支持在首次请求前增加有上限的等待，但尚未证明异常值的具体来源或后续 IPMI 请求一定成功。

B2b 把等待放在第一次 Get Device ID **之前**：只读取状态及 PCI 配置，最多 31 次、间隔 1 秒，连续三次 00 后立即继续设备识别和基线扫描。已准备好的接口通常只需两次一秒等待；持续 FF 最多等待约 30 秒。**等待期间不发送命令，也不自动执行 I 或 F。**

## 运行步骤

1. 保留已有日志。把本包 `USB` 文件夹**里面**的 `EFI` 和 `HERO-PROBE-USB.TAG` 一起更新到 FAT32 U 盘根目录。启动后确认标题为 **HERO IPMI FAN B2b**。使用当前 HERO BIOS 3107，无须刷 BIOS 或降级。
2. 按屏幕提示 **E/P**。它会自动记录 `READINESS_SAMPLE`，无需再按 S。看到 `READINESS_IDLE_STABLE` 后，程序才首次请求设备身份和传感器目录。
3. 若成功读出基线：有 **F** 就按 F 做原定的 CHA_FAN1 测试；若先提供 **I**，说明符合重新初始化条件，可先执行一次与 B1 相同的 I，再看是否提供 F。没有 I/F 提示时保留日志，不绕过检查。
4. F 后等待约 **30 秒**，按 **R** 再读一轮；同时可查看 BMC 网页的 **MB_CHA_FAN1**。截图中的 BIOS 对照值是 2884 RPM，BMC 当前定义按 120 RPM 量化，所以约 2880 RPM 可以是合理的近似值，仍需实际确认对应关系。
5. 按 **Q** 完成记录；日志关闭后再按 **Q** 返回启动菜单。若等待或通信阶段已自动停止，日志关闭后按一次 Q 即可。提供最新的 `HEROIPMI-xxx.TXT`；若完成 F，也补充 BMC 网页读数。

I 和 F 的作用与 B2 相同：I 执行候选初始化，F 修改单项转速映射并启用扫描。**这些操作会改变 BMC 运行状态，Q 不撤销已完成的修改。**如只想检查连接，可以在基线读取后直接 Q 退出。

## 等待怎样停止

- FF：保持只读，清零连续 00 的计数，在同一时间窗口内继续。
- 三次连续 00：完成等待，然后发出首次 Get Device ID；00 只是入口条件，命令的成功响应才是通信验证。
- 31 次采样仍不满足条件：输出 `READINESS_STOPPED_NO_REQUEST`，不发 IPMI 请求。
- 遇到其他非零状态、PCI 身份/BAR/内存解码变化、读取失败、日志失败或计时等待失败：立即停止，不清空数据寄存器、不重置 BMC、不接管忙接口。
- 已进入请求传输后再次出现 FF 或其他错误：停止，不重新等待，不重放请求。I/F 的命令也没有自动重试。

三次 00 是本次工程针对 004 证据采用的保守入口条件，不代表所有合法 KCS 状态都必须是 00。例如何种情况下应处理 attention 状态，不在本次自动流程内。

E 仍只临时设置扩展卡 PCI Command 的内存访问位，并在正常退出及已处理错误路径尝试恢复、读回。死机、断电或无法确认仍是同一设备时不能保证恢复；日志会区分已确认与未确认结果。本版要求日志可写才开始等待或发送请求。

## 当前已知结果

- B1：4 项温度与 4 项电压已有实机可用读数，风扇项仍不可用。
- 003：首次状态 FF 即停止，没有执行风扇修改。
- 004：FF 后，31 次状态读取全部 00；没有继续发送 IPMI 请求，所以仍无 B2 风扇实测结果。
- B2b：加入启动等待，尚未在目标机运行。即使 `FAN_SEQUENCE_ACCEPTED`，也必须检查传感器可用状态、实际 RPM 及更新情况。

B2b 不加载供体 DXE，也不包含 BIOS/BMC 刷写镜像。主板其余风扇/水泵、自动开机初始化及完整 BIOS 集成仍待验证。

## 验证与依据

最终 EFI 机器码通过 148 个离线场景：保留的 121 个基础/B1/B2 场景，加上 27 个启动等待场景。新增检查涵盖 FF 转 00、最后一次采样才满足条件、来回变化、持续 FF、忙/输出待取/错误/attention 状态、各阶段日志失败、PCI 变化、等待失败，以及请求发送前后再次 FF 不重试。还检查了等待完成不会自动执行 I/F，而明确按 I/F 后原流程仍可运行。

离线设备是模拟的，真实目录/读数夹具来源于旧实机日志；`example-MOCK-*` 不是新实机成功记录。真实 004 的分析与截图在 evidence 中。源码及脚本依赖现有 BIOS 工作区工具和历史证据，不能单独视为安装环境。

KCS 的状态和输入/输出标志含义核对了 [Linux v6.12 KCS 实现](https://github.com/torvalds/linux/blob/v6.12/drivers/char/ipmi/ipmi_kcs_sm.c#L164-L172)。该来源支持 00 的状态解释，不证明本次 FF 的硬件原因，也不规定本工具的三次采样策略。
