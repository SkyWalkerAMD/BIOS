# Fixed UEFI bootstrap for Linux capacity diagnostic candidate 01

This directory belongs to the local simulation task. It does not authorize BMC access, target deployment, reboot, flash writes, or hardware testing. Only the custom initramfs from the sibling PID1 review may be used; the downloaded stock Alpine initramfs is never booted.

`source/bootstrap.c` accepts no interactive command line or media configuration. `build_loader.py` embeds the exact kernel/initrd lengths, SHA-256 hashes, and one reviewed command line from a JSON contract. Firmware-supplied load options do not override it. A contract must be explicitly frozen by the parent/PID1 review before the result is called an approved candidate.

The application disables the UEFI watchdog, checks its own LoadedImage DeviceHandle and `\EFI\BOOT\BOOTX64.EFI` path, and opens only that device's filesystem. The filesystem's read-only flag is logged as metadata. A false flag is explicitly labeled `SOURCE_IMMUTABILITY_NOT_PROVEN`; it does not enable writes. This policy was approved by the parent because some USB optical transports omit the read-only flag even for an immutable ISO. The loader reads `\LINUX\VMLINUX.EFI` and `\LINUX\CAPACITY01.IMG` using EFI_FILE_MODE_READ. Lengths, full-file SHA-256, and EOF are checked before executing any payload. Reads have fixed 1 MiB maximum requests, fail on short/error reads, and have no retry or device-search path. Firmware protocol calls can themselves stall; this application does not claim to impose deadlines inside firmware.

The kernel receives the already verified RAM buffer through UEFI LoadImage with a same-device file path. Its LoadedImage parent, DeviceHandle, and path are checked again. The initrd is delivered from its verified RAM buffer using the Linux vendor media device path and EFI_LOAD_FILE2_PROTOCOL. An existing provider at that path is rejected. The callback accepts only BootPolicy FALSE and the remaining EndEntire path, negotiates exact size, and copies only those pinned bytes. It never opens a second initrd file or follows command-line `initrd=` paths.

The pinned kernel's EFI stub may delete a pre-existing `RandomSeed` variable before `efi=noruntime` takes effect. The bootstrap therefore performs two read-only size queries under `LINUX_EFI_RANDOM_SEED_TABLE_GUID`: once before reading payloads and once immediately before StartImage. Both must return exact EFI_NOT_FOUND and leave the requested length zero. All other statuses stop. No buffer for seed contents is supplied, and no seed contents or size are printed. There is no firmware-service call between the successful final query and StartImage. These are absence preconditions, not an atomic lock on firmware variable storage. The separate kernel review must bind the exact binary/config/source and cover other boot-time effects.

Any failure prints a stable `LC01_BOOT_STOP` reason and enters a nonreturning loop of bounded waits. Even an EFI_SUCCESS return from the kernel is treated as failure. The application does not call Exit, ResetSystem, SetVariable, file Write/Delete/SetInfo, block WriteBlocks, or flash interfaces. It performs no disk search, networking, NVRAM persistence, fallback boot, or automatic restart. External BMC/hardware watchdogs remain outside its control, and a failed firmware watchdog-disable call cannot establish that the firmware timer stopped.

These restrictions describe the bootstrap. They do not mean Linux has zero system effects. Kernel boot changes RAM and device/driver state, performs standard ExitBootServices, may measure initrd/command-line data into TPM PCRs, and may install EFI configuration tables. The sibling kernel/PID1 review defines the remaining approved effects and runtime-service restrictions. Hash pinning detects payload mismatch but is not an independent Secure Boot root of trust.

Build and test artifacts, exact hashes, and results are written below this directory. QEMU/OVMF tests use isolated regular image files, no network adapters, no host-disk or device passthrough, and no BMC connection. Test-only RuntimeServices fault-injection DXE images are inserted solely into isolated OVMF copies under `tests/`. They are never part of the production ISO. An OVMF run that refuses its non-target board identity is a valid transport/refusal test, not an ASUS W790 SAGE SE hardware pass.

The boot ISO uses a 31 MiB FAT16 El Torito image, whose entire extent fits the 16-bit boot-sector count. An early 64 MiB/underspecified-count test failed before loading the application because OVMF exposed an undersized boot partition. That failed construction is retained only as historical test evidence; it is not a release layout.

The locally frozen candidate is `candidate/media/boot.iso`, with exact byte bindings in `candidate/media_manifest.json`. `LOCAL_VALIDATION.md` and `candidate/verification.json` distinguish final-ISO Linux tests from synthetic EFI fixtures. The actual Linux tests use deterministic QEMU instruction timing because the earlier host-clock TCG profile panicked during early IO-APIC timer initialization. Production bytes and command line contain no timer workaround. That simulator setting is not a physical timing model or an ASUS hardware qualification.

References are the pinned Linux 6.12.114 files under `reference/`, particularly the EFI-stub helper's LoadFile2 route and x86 PE/COFF boot protocol. Official supporting documentation: [Linux EFI stub](https://docs.kernel.org/admin-guide/efi-stub.html), [Linux x86 PE/COFF boot entry](https://docs.kernel.org/arch/x86/boot.html), and [EDK II LoadFile2 ABI](https://github.com/tianocore/edk2/blob/master/MdePkg/Include/Protocol/LoadFile2.h).
