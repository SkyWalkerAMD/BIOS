# HERO 3107 IPMI 设置适配 M1

M1 增加原生 UEFI HII 设置页面、独立配置保存和开机初始化逻辑。它沿用 B2c 已在你的 HERO 上成功执行的四条初始化命令；新驱动本身尚待 HERO 实测。

你反馈 CPU 温度和电压已有读数，这是现有初始化方案的实机进展。M1 没有新增风扇映射或 PWM 控制，不能据此宣布风扇适配完成。

## 本版功能与验证范围

| 项目 | 本版状态 |
|---|---|
| `Auto initialize at boot` 开关 | 已实现，默认关闭，保存到独立变量 |
| BMC 身份、目标传感器数量、初始化结果和失败锁状态 | 已实现；按 `Refresh BMC status` 才查询硬件 |
| `Initialize now...` 手动初始化 | 已实现；要求先保存启用设置，且通过主板、版本、BMC、SDR 检查 |
| 固件开机自动初始化 | ReadyToBoot 回调已实现并通过离线执行测试；HERO 上的固件调度尚待验证 |
| 独立设置页面 | 已用实际发布 EFI 在 QEMU/OVMF 中打开、保存、重启后读回 |
| 华硕 BIOS 的 Advanced/Server Mgmt 固定入口 | 尚未验证；注册标准 HII 表单不保证 AMI 自动增加顶级菜单 |
| 风扇、网络参数、远程刷 BIOS | 本版未实现；原有 B2c 的 F 仍缺实机验证 |

目标只接受 **ROG MAXIMUS Z790 HERO，BIOS 3107**，以及目前实测 BMC 1.3.13 的精确 Device ID 回复。3001、其他主板/版本或不同 BMC 身份会停止硬件初始化。

## 先做 U 盘验证，不需要刷 BIOS

1. 将压缩包内 **USB 文件夹的内容**复制到 FAT32 U 盘根目录，保持目录结构：

   ```text
   /HERO-IPMI-M1.TAG
   /EFI/BOOT/BOOTX64.EFI
   /EFI/HERO/HeroIpmiM1.efi
   ```

2. 从该 U 盘的 UEFI 启动项启动。它会临时加载驱动并打开固件自己的设置浏览器。若打不开，记录屏幕上的 `Session result` 错误码。
3. 首次先保持自动初始化关闭，选中 **Refresh BMC status** 并按 Enter。它读取 BMC 身份和完整传感器记录；必要时暂时启用 PCI 内存解码，结束后恢复。
4. 验证设置保存：用空格切换 **Auto initialize at boot**，选中 **Save configuration** 按 Enter。`Saved auto-init` 应显示保存后的值。退出并重新从 U 盘启动后，应仍能读回该设置。测试结束可再次保存为关闭。
5. 如需验证手动初始化，先将开关保存为启用，再进入 **Initialize now...**，移动到 **Confirm initialization now** 按 Enter。说明文字本身不会执行命令。完成后按 Esc 返回主页查看结果。
6. 最后按 Esc 退出页面，等屏幕显示 **Audit saved**。U 盘根目录会生成 `HERO-M1-000.TXT`、`001.TXT` 等文件；已有日志不会覆盖。把此次日志发回即可继续适配。

**U 盘临时加载发生在本次 ReadyToBoot 之后。保存开关不会把驱动安装进 BIOS，也不会让它在以后的开机中自动加载。** U 盘阶段验证菜单、配置保存、读取和手动初始化；真正的开机自动执行属于后续固件实机验证。

如果 BMC 已有完整的 16 个目标 SDR 且 `VERSION_ERR` 已清除，初始化会报告 `Already initialized` 并跳过四条 OEM 命令。这是预期行为，不需要为了测试而重置 BMC。

## 失败时如何处理

- `KCS error state`：M1 不自动中断 KCS 通信，也不自动重置 BMC。退出保存日志；已有 B2c 的 K 恢复流程仍是独立诊断步骤。
- `attempt remains locked`：先保留并检查日志。本次尝试记录会跨重启保留，防止每次启动重复发送未完成的初始化命令。
- 清除失败锁必须先将自动初始化**保存为关闭**，然后进入 **Clear previous attempt lock...** 并选中确认操作。清锁不回滚 BMC，也不解除同一次驱动运行中的尝试次数限制。
- `PCI restoration unconfirmed`：停止本轮测试，提交日志确认 PCI 恢复问题。

日志保存在驱动内存中，退出 U 盘菜单时才完整写入文件。死机或断电会丢失尚未导出的日志；初始化前写入的失败锁仍用于阻止自动重放。清锁前先保留现有诊断结果。

## 固件候选的含义

工作区另有 `HeroIpmiSetupM1.ffs` 和 `HERO-3107-IPMI-M1-UNSIGNED-REVIEW.CAP`，用于检查固件集成；**U 盘测试包不包含 CAP，也不执行刷写。**

候选以官方 3107 为基础，保持全部 717 个原始 FFS 文件不变，只在已确认的空闲区加入一个 DXE。重新提取后共 718 个文件；PE、FFS 头和 FV 头检查通过。依赖使用标准 PCI 枚举完成 GUID `30CFE3E7-3DE1-4586-BE20-DEABA1B3B793`，没有沿用旧 R1 错误的 `72338391...` 依赖。

该候选没有 ASUS 重新签名；结构检查不能证明刷写工具接受它、平台启动验证通过，或 AMI 已建立 Advanced 菜单入口。因此它仍是离线审查候选，不是已完成实机验证的可交付 BIOS。

## 配置和复现

仅使用私有命名空间 `C2614243-A877-4ACF-A458-CE2904EC3E10` 下的 `HeroIpmiCfg`（8 字节）与 `HeroIpmiAttempt`。不复用 ProArt 的 `Setup`/`ServerSetup` 偏移，不写 HERO 原有 Setup 配置。配置未改变时不重复写入。

`verification.json` 记录发布驱动的 51 项机器码执行测试。输入包括历史 A2/B1 的真实回复，故障及状态转移为模拟；这不是新的实机日志。`vm/results.json` 记录 QEMU/OVMF 的菜单验证，`capsule-verification.json` 记录固件结构和字节对比。

源码与构建脚本一起提供。工作区内依次运行 `build.py`、`verify.py`、`build_capsule.py`；需要现有 `tools/`、历史测试脚本及回复记录。菜单 ABI/IFR 参考固定版本的 [TianoCore EDK II](https://github.com/tianocore/edk2/tree/edk2-stable202502)，具体来源及摘要见 `source/reference/sources.json`。
